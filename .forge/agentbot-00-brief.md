# AgentBot 立项简报

> 事实底座：`.forge/agentbot-ref-research.md`。标 `[假设]` 的论断无公开来源支撑。
> 已决前提见 `.forge/state.json` Q1–Q5（插件形态、首版运行时、单用户、群聊、会话归属）。

## 一句话

一个本地 Web 的「AI 同事」工作台：你建一组有名字、有记忆、有权限边界的 Bot，每个 Bot 可以绑定不同的 agent 运行时（ZCode / Codex / [CC] / DSH / 任何 ACP agent），由本产品编排它们协作，但**执行永远交给用户已经装好的 agent**，自己不实现 agent loop。

## 问题陈述

现有三个对标产品都不是「不好用」，而是**结构性错位**：

**1. 绑死单一宿主。** DS Bot 和 DeepSeekBot 都是 DSH 插件，离开 DSH 就不存在（调研 §1.2、§1.3）；Grok Bot 绑死 xAI 云（§1.1）。真实场景：一个团队里有人用 Codex 付了年费、有人公司只批 [CC]、有人本地跑 DSH 接自建模型。今天想让他们共用一套 Bot 团队，只能让所有人迁到同一个宿主——这跟「让全公司统一用同一个编辑器」一样不现实。

**2. Bot 的能力被宿主决定。** 宿主有什么工具、MCP、Skills，Bot 就只有什么（§1「共同局限」2）。真实场景：用户想让「审稿 Bot」只能读文件、不能跑 shell，让「运维 Bot」能跑 shell 但只能碰 `/srv`。在插件形态里这做不到，因为权限模型是宿主的，插件只能整体继承。

**3. 无法混用不同 agent。** 不能让「研究员 Bot 用 Gemini 长上下文、工程师 Bot 用 Codex、审稿 Bot 用本地模型」（§1「共同局限」3）。真实场景：一个任务里，调研阶段需要便宜的大上下文模型，实现阶段需要强工具调用，审查阶段需要另一个模型避免自审偏差。单一宿主下，用户只能开三个窗口、手动搬上下文——上下文搬运正是最贵的人工。

**4. 执行位置没有中间态。** 要么在云 VM（隔离但重、账号要代登录），要么完全污染本机（§1「共同局限」4）。真实场景：用户不敢让 Bot 在自己主仓库上直接改，但也不想为每个小任务开一台云机器。

## 目标用户与场景

**A. 独立开发者 / 小团队技术负责人（首要）**
手上有 Codex 订阅 + [CC] + 本地 DSH 三套环境。日常：早上在群里丢一句「把这个 issue 修了，顺便补测试」，然后去开会。回来要看：谁改了什么、跑没跑测试、花了多少额度。
价值点：一个群里三个 Bot 各用自己最划算的运行时，任务派下去不用人肉搬上下文。

**B. 需要「非工程角色 Bot」的产品/运营（次要）**
不写代码，但要一个「竞品监测 Bot」每周扫网页、一个「文档 Bot」维护内部知识。她的机器上装了 Gemini CLI（公司发的）和自己的 ZCode。
价值点：她不需要理解 ACP 或 CLI 参数，只需要在 UI 里给 Bot 选「用哪个 agent」——这个选择对她是可见的产品概念，不是配置文件。

**C. 多 agent 混用的验证者 / 折腾型用户（早期种子）**
已经用 `@openacp/cli`、`acp-bridge` 这类工具在终端里桥接 agent（§2 生态现状）。痛点是没有 UI、没有群聊、没有权限审计、没有用量。
价值点：他要的是「同一套 Bot 定义，今天绑 Codex，明天绑 Gemini，人格和记忆不丢」。

> 场景 A 必须成立：**同一个群里，研究 Bot 跑 Gemini、实现 Bot 跑 Codex、审查 Bot 跑 [CC]**，三者通过统一事件流呈现在同一个群聊里。

## 成功标准

1. **新增一个原生 ACP 运行时 ≤ 1 个 adapter 声明文件、≤ 200 行、零核心改动、零 schema 变更**；从零到该运行时能在群里回第一条消息 ≤ 1 小时。（验证 C1 是否真的成立）
2. **一次 ≥ 3 个 Bot、≥ 2 种运行时的协作任务，在无人逐条干预下跑完并交回可读报告**；期间人工介入 ≤ 1 次（仅权限批准）。
3. **任意时刻，用户能在 Bot 列表一屏内看到每个 Bot 当前绑定的运行时、执行位置、session 状态**；随机抽查 5 个 Bot，用户 100% 能正确说出它在哪个 agent 上跑。
4. **一次群聊任务结束后，用量页能按 Bot × 运行时拆分 token 消耗**，且 headless 模式的倍率差异被标注（[CC] 约 3×，§3）。
5. **冷启动到发出第一条消息 ≤ 60 秒**，且用户已有的 agent 登录态无需重新配置 `[假设：沿用各 CLI 自身凭据]`。

## 首版范围（In）

- **Bot 作为持久实体**：名字、人格、职责、头像、默认运行时绑定；换会话仍是同一个 Bot。
- **私聊 + 群聊**：群聊含主持机制——默认由主持 Bot 决定谁发言，不默认全员回复。
- **权限卡片**：运行时抛上来的授权请求归一成卡片（批准/拒绝/记住），叠加 Bot 级目录/工具边界，全程留审计。
- **用量可见**：按 Bot / 运行时 / 时间维度统计。
- **统一事件流**：所有运行时的事件（消息增量、思考、工具调用、计划、权限请求、用量、结束、错误）呈现为同一套 UI 语义。
- **三条通道各一个参考 adapter**：ACP 通道（[CC] via `claude-code-acp` 或 Gemini CLI）、原生协议通道（Codex app-server）、CLI 通道（ZCode 或 DSH，见待确认 1）。
- **执行位置**：`local` 与 `git worktree` 两种，作为 Bot/adapter 的可见属性。
- **会话归属**：产品层持有会话真相；运行时 resume 可用则续接，不可用则产品层重建上下文（Q5）。
- **单用户本地 Web**，本地服务需 token 鉴权防同机其他程序访问（Q3）。

## 首版不做（Out）

- **自研 agent loop / 模型调用 / prompt 编排框架**——那是运行时的事（§5）。
- **云 VM 托管与账号代登录**——Grok Bot 的重模式，首版不碰（§5、C7）。
- **IM 平台接入**（飞书/Slack/Discord/QQ/微信）——只留出站 webhook 口子（§5）。
- **Bot 市场 / 分享 / 导入导出**（§5）。
- **多租户账号体系、团队权限、SSO**（Q3、§5）。
- **移动端 / 桌面原生客户端**——首版只有 Web。
- **常驻 Routine 轮询**——已决：定时任务以最小版进首版（一次性延迟 + 周期触发），但不做常驻轮询与"Bot 自主发起对话"。
- **记忆的 Git 可视化（commit/diff/分支）**——见待确认 3，已决为产品层结构化记忆。
- **Bot 主动发起对话**（无用户触发时自主行动）。

## 核心概念定义

- **Bot**：产品层的持久实体。有名字、人格、职责、长期记忆、权限边界和默认运行时绑定。它不是进程、不是会话、不是模型；进程杀掉、换会话、换运行时，它还是同一个它。
- **Agent Runtime**：用户机器上已安装的、真正执行任务并调用模型的 agent 程序（ZCode、Codex CLI、[CC]、DSH、Gemini CLI…）。它自带 agent loop、工具、MCP、Skills、权限模型。本产品只驱动它，不实现它。
- **Adapter**：描述「某个运行时怎么启动、说哪种协议、上报哪些能力、事件如何映射成统一事件」的声明 + 薄代码。新增运行时 = 新增 adapter，不改核心。
- **Session**：一次与某个运行时的具体执行上下文（运行时侧 session id + 产品侧消息/事件记录）。Bot 与 Session 是 1:N；Bot 换运行时会开新 Session，Bot 本身不变。
- **Channel**：承载对话的产品层容器（私聊 / 群聊 / 任务线程），决定「谁看得见、谁能被 @」。Channel 是参与者集合，与运行时无关。
- **Assignment**：一次被显式委派、有明确交付物和结束状态的任务，独立于聊天消息流，完成后交回报告。区别于「在群里随便问一句」。
- **Memory**：Bot 跨 Session 保留的信息。分两层：产品层可编辑的长期记忆（人格/偏好/事实，**是真相**）与运行时自己的上下文（可丢）。运行时换了，产品层记忆仍在。
- **Permission Request**：运行时在执行中抛出的「我要做 X，允许吗」。它被归一成产品内卡片，与 Bot 级边界共同构成两层权限：外层定「这个 Bot 允许碰什么」，内层定「这一次具体动作批不批」。

## 不可动摇的架构前提

| # | 前提 | 违反的后果 |
|---|---|---|
| C1 | 协议分层（ACP / 原生协议 / CLI 兜底），新增运行时只加 adapter | 每接一个 agent 都变成一次重构，接到第三个就做不动，产品承诺作废 |
| C2 | Bot ≠ Agent 进程，Bot 是持久实体，运行时是可替换后端 | 产品退化成某个宿主的皮肤，与 DS Bot / DSB 无区别，失去存在理由 |
| C3 | 能力靠运行时上报，不靠硬编码假设 | UI 出现假按钮（如对不支持的运行时显示「计划」面板），用户以为产品坏了 |
| C4 | 权限必须在产品层可见，不重新发明权限 | 无人值守时 agent 静默执行危险操作，或反过来所有操作都卡死，两种都不可用 |
| C5 | 所有运行时事件归一为统一事件模型 | 每加一个运行时 UI 都要改，多 Bot 群聊无法统一呈现，成本线性上升 |
| C6 | 长会话成本必须内建控制（压缩、按 Bot 用量、群聊不全员回复） | 群聊一次对话烧掉一天配额，产品直接不可用（多 agent 约 15× 普通对话） |
| C7 | 执行位置是显式可见的选择（local / worktree / container / remote） | 用户不知道 Bot 改了哪个目录，多 Bot 互相踩文件，信任崩塌 |

## 风险与未知

| 风险 | 说明 | 缓解方向 |
|---|---|---|
| 运行时协议不稳定 | ZCode headless stdio 无公开 schema；ACP v2 仍在演进（§6 开放问题 1） | adapter 做版本探测与能力降级；对未知行容忍丢弃；每个 adapter 配契约测试 |
| 上下文成本爆炸 | 多 agent 约 15× 普通对话（C6）；headless 配额更高 | 群聊默认主持人不全员回复；每轮只注入人格 + 核心记忆；压缩可见；用量按 Bot 拆 |
| Windows PTY 兼容 | ConPTY 与各 CLI 交互式模式兼容性未验证（§6 开放问题 4） | 优先 stdio / JSON-RPC，非必要不走 PTY；必须 PTY 时启动探测，失败降级为非交互 exec |
| 多 Bot 并发改同一工作区 | 群聊里多个 Bot 同时写同一仓库会互相覆盖（§6 开放问题 5） | 群聊任务默认 worktree 隔离；合并回主工作区需显式批准；同文件写串行化 |
| session resume 不一致 | 各 adapter 的 `session/resume` 一致性未知（§6 开放问题 3） | 产品层持有会话真相，resume 失败即重建上下文（Q5 已定） |
| 用户额度被本产品消耗 | 用户在 agent 里看到的用量与本产品统计可能不一致 | 用量页标注 headless 倍率；不代管凭据，沿用各 CLI 自身登录 |

## 与已有产品的差异表

| 维度 | Grok Bot | DS Bot | DeepSeekBot | 本产品（首版） |
|---|---|---|---|---|
| Bot 持久性 | 强：具名 Bot + 长期记忆 + Routine | 中：Bot 是 DSH 内的配置实体 | 强：Bot + 记忆 + 导入导出 | 强：Bot 独立于运行时与会话；**但无 Routine，弱于 Grok** |
| 执行后端 | 固定：xAI 云 VM | 固定：DSH 宿主 | 固定：DSH 宿主 | 可替换：Bot 绑定运行时，可换 |
| 记忆 | 云端长期记忆 | 宿主上下文 | **Git 工作树，可看 commit/diff，可多机同步** | 产品层结构化记忆；**可视化弱于 DSB** |
| 群聊 | 无（私聊/委派为主） | 有，管理员 Bot 默认回复控成本 | 有，@ 谁谁回，Bot 间可接话 | 有，主持 Bot 决定谁发言（与 DS Bot 同思路） |
| 扩展方式 | 平台侧封闭 | npm 插件，依赖 DSH | 插件 + 市场 + IM connector | 写 adapter 声明；**无市场，门槛高于 DSB** |
| 跨 agent 混用 | 不可能 | 不可能 | 不可能 | **核心差异点** |
| 执行位置 | 云 VM（隔离、重） | 本机（轻、污染） | 本机 | local / worktree 可选；**无容器与远程，弱于 Grok 隔离性** |
| 部署门槛 | 零安装，但要 xAI 账号 | 装 DSH | 装 DSH | 需要本机已装 agent；**门槛最高** |

诚实结论：本产品在三项上明确更弱——**部署门槛、记忆可视化、生态（市场/IM）**。唯一不可替代的价值是「跨 agent 混用 + Bot 独立于宿主」。若这条不成立，产品没有存在理由。

## 待确认

1. **首版 CLI 通道先做哪个运行时？**
   - A：ZCode（用户主用，headless stdio）
   - B：DSH（有 `dsh web`，但深度接入要写 Cordis 插件，会锁宿主）
   - 建议 **A**。ZCode 是用户日常环境，验证 CLI 兜底通道的真实成本；DSH 走 CLI 驱动即可，二期再评估插件形态。

2. **定时任务 / 常驻 Routine 是否进首版？**
   - A：进，只做最小版（一次性延迟 + 周期触发，无常驻轮询）
   - B：不进，首版只手动触发
   - 建议 **A 的最小版**。「AI 同事」的核心预期是「我不在时它也在干」，完全没有会让产品退化为多 Bot 聊天工具；但常驻轮询会把成本和 Windows 进程管理风险一起放大。

3. **Bot 记忆首版做成什么形态？**
   - A：产品层结构化记忆条目（可编辑的 markdown/JSON + 自动摘要）
   - B：每个 Bot 一个 Git 工作树，可看 diff（对齐 DeepSeekBot）
   - 建议 **A**。B 是 DSB 的强项，正面硬拼成本高且与「不做自研 agent」无协同；A 能保证换运行时记忆不丢，这才是本产品的差异点。

4. **Bot 默认权限边界有多宽？**
   - A：默认只读 + 写操作需批准（安全，但无人值守时会被卡片打断）
   - B：默认放行（体验顺，但本机风险由用户承担）
   - 建议 **A，并允许用户对单个 Bot 预授权**。无人值守是核心卖点，但没有默认安全边界时，一次误删就会让用户彻底不信任产品。
